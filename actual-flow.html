01 · Bottom line

The orchestration is where the vision breaks.

The codebase contains solid local pieces: atomic writes, a real dispatcher, usable extraction, course scaffolding, and a thoughtful gate vocabulary. The problems are at the seams between them.

The shortest accurate summary is this: TextCourses currently has two front doors and several disconnected state machines. The public skill documentation does not call the new conversational dispatcher. The dispatcher can discover a topic and open Gate 1, but the topic-only path does not create a course after the gate is answered. The course that does get created stores its human notes under the machine substrate, because the notes compiler derives the course root from the location of course.toml.

None of those are cosmetic issues. They change what a learner can reach, what a learner can see, and what a “completed” section means.

The practical result A learner who types a topic and follows the on-screen gate can end up with research files, a cleared checkpoint, and no course. A learner who drops in a PDF can get a course, but the compiled chapter notes land inside .tc/notes/, while the visible notes/chapter-01.md remains a scaffold.

The front door is split

skills/tc/SKILL.md tells the agent to call checkpoint, extractor, and teaching commands directly. It never calls tc.py dispatch, the state machine that is supposed to be the single door.

→ points 1, 3, 4

Topic-only creation dead-ends

Gate 1’s “proceed” response returns state: creating_course, but no course builder runs. The next input starts a new research gate for the slug 1.

→ points 4, 5, 8

The clean canvas is not clean

Research is written to research/, .tc/research/, and sometimes _tc/research/. Course notes are written to .tc/notes/. Human notes are not updated.

→ point 2

Completion is asserted, not enforced

The last concept tick auto-compiles notes and marks the section review. There is no learner sign-off, no history scrub, no auto mode, and no status board.

02 · Method & naming

What counted as “implemented”

A feature is not implemented because a markdown file says it is, a badge calls it aligned, or a test asserts a related helper. It is implemented when a learner can reach it, it persists the promised artifact, and the state transition is covered by a test.

Evidence standard

All four conditions had to hold:

  1. A reachable code path from the public entrypoint.
  2. The promised file or state change on disk.
  3. The behavior a learner would actually experience.
  4. A test that exercises that path, not a legacy mock layout.

What was inspected

The public skills, the dispatcher, bootstrapper, checkpoint manager, scout, paper/book fetchers, extractor, course builder, source mapper, coverage auditor, teaching engine, notes compiler, indexer, practical evaluator, diagnostic tester, docs, tests, and the flow.html specification.

What was executed

The full test suite (python -m pytest -q, 326 passed) and two disposable workspace simulations through tc.py dispatch: a topic-only run and a drop-in PDF run. No repository runtime files were modified for this review.

Read the folder names carefully

The vision says _tc. The runtime uses _tc/, .tc/, and research/ for different things. Confusing them makes every later design decision ambiguous.

_tc/
Engine scripts and legacy research. Contains scripts/, cache/, and research/. This is the folder the learner’s vision literally names.
.tc/
Hidden machine state. Contains workspace checkpoint.json, and per-course course.toml, memlog.md, source-map.toml, coverage-ledger.md, session.jsonl, plans, and RAG databases.
research/
Visible research dossier. The scout writes dossier.md, sources.json, sources.toml, gold standards, and critiques here. It is then mirrored into .tc/research/.
.tc/research/
Second copy of the same research. The scout writes identical dossier artifacts here and also writes the same critique under three names.
courses/<slug>/notes/
The intended human canvas. Course scaffolding creates the chapter files here. The notes compiler does not update them when the course uses the real .tc/course.toml layout.
courses/<slug>/.tc/notes/
Where compiled chapter notes actually go. This is the path bug: the compiler sets course_dir = manifest_file.parent, which is .tc/, not the course root.
Ambiguity that must be settled before code changes The proposal’s “canonical” layout places raw research at research/<slug>/sources/ outside .tc/. The learner’s point 2 says all study material, research, and docs stay in _tc, with only notes outside. Those are not the same contract. The proposal must choose and defend one, not silently redefine “clean canvas.”

04 · Observed runtime

Two front doors, one dead end

The public skill and the Python dispatcher are not the same workflow. The dispatcher is closer to the intended state machine, but it is not what /tc tells the agent to run. This single split explains a large part of the vision gap.

Lane A — the skill the learner invokes /tc · public
A1Read skills/tc/SKILL.md. The footer says tc is the single front door.
A2Check a pending gate via checkpoint_manager.py status.
A3Respond via checkpoint_manager.py respond when a gate exists.
A4Auto-ingest dropped books via extractor.py auto-ingest.
A5Teach an active course via teach_engine.py session.
A6End with the 4-option fork. No course-creation call appears in the documented workflow.

There is no tc.py dispatch call, no course_builder.py create call, and no dashboard step. The lane can teach a course that already exists. It does not document how a new course is created.

Lane B — the dispatcher that models the flow tc.py dispatch · parallel
B1Intake if profile/preferences.md or plan/preferences.md is missing.
B2Discover a topic, slugify it, and look for dropped documents.
B3Scout when no documents were found: curated sources, dossier, duplicate writes.
B4Open Gate 1 (material acquisition) and wait for input.
B5Answer “1” → returns creating_course and exits. No builder is invoked.
B6Drop a PDF instead → auto-ingest → create_course → Gate 2 → teaching. This branch works.

The working creation path is the drop-in branch. The topic-only branch is the one a learner naturally takes, and it is the one that does not continue to a course.

Split-brain consequence A code path can be “implemented” in the dispatcher and still be unreachable from the public experience. The flow.html page describes the dispatcher’s intended state machine; the skill the learner actually invokes does not use it.

Creation path: what happens when the learner types a topic

Step 01 · workspace

bootstrapper.py creates the canvas

It creates the engine folder, the hidden state folder, a visible research folder, a root sources/ folder, plan/sources/, profile/, roadmap/, courses/, and portfolio/. There is no status-board step and no single research root.

bootstrapper.py → dirs_to_create
Step 02 · intake

The only prompt is a three-question onboarding prompt

It asks for a goal/topic, experience level, and whether the learner wants practicals. It does not ask for interactive vs auto, and it does not offer a straight-to-teaching mode. Once preferences exist, the prompt is skipped on future runs.

tc.py → intake_needed
Step 03 · topic

The input becomes a slug and a research run

If no course exists, a multi-word input is treated as a topic. The dispatcher slugifies it, looks for dropped documents, and runs the scout if none are found. The scout invokes curated paper/RFC harvesting and book discovery, then writes dossier artifacts.

tc.py → run_scout(slug, topic)
Step 04 · gate 1

Research ends at the acquisition gate

The learner sees recommended books, downloaded specs, a drop-in instruction, and two choices: proceed with open docs or wait for a file. There is no “these are the best sources, approve them” list and no loop to request more research.

checkpoint_manager.py → acquisition_gate
Step 05 · dead end

“Proceed with open docs” does not create the course

The gate clears and the dispatcher returns state: "creating_course" with the message “Synthesizing curriculum…”. The function then exits. There is no call to create_course, no approval gate, and no course directory.

tc.py → state: creating_course (no builder)
Step 06 · loop

The next input starts a new research gate

Because no course now exists, the next input is interpreted as a new topic. Typing 1 produces a course slug literally named 1, a fresh scout run under research/1/, and another acquisition gate. The loop can repeat.

tc.py → new slug “1” → acquisition_gate
Step 07 · alternate branch

A dropped document changes the outcome

If a PDF or EPUB is discovered, the dispatcher auto-ingests it, calls create_course, and opens the curriculum approval gate. This is the branch that reaches teaching. It is not the branch the visible topic-first invitation leads to.

discovered_docs → create_course → approval_gate

Reproduction: topic-only dispatch

Run in a disposable workspace. The commands are the same shape used by the UI; the output is summarized from the returned JSON. 

tc.py dispatch --input "Distributed Storage" --workspace <tmp> --json
# → state: acquisition_gate
#   slug: distributed-storage

tc.py dispatch --input "1" --workspace <tmp> --json
# → state: creating_course
#   action: proceed_open
#   courses/ is still empty

tc.py dispatch --input "1" --workspace <tmp> --json
# → state: acquisition_gate
#   slug: "1"
#   research/1/ was created

Observed in a disposable workspace; no course directory was created by the first gate response.

Teaching path: what happens after a course exists

Gate 2 · approval

The course has already been scaffolded before the learner reviews it

create_course writes .tc/course.toml, the overview, notes scaffolds, memlog, generic section plans, and a source map. Only then does create_approval_gate render the chapter outline and wait for “start lesson 1” or “adjust roadmap.”

create_course → create_approval_gate
Session · context

The engine returns context, not the lesson itself

get_teaching_session resolves the active section and concept, reads preferences, checks practical status, and returns a fork and source excerpts. The agent is responsible for the actual explanation. This is a reasonable division of labor; the gap is what happens next.

get_teaching_session → context + fork_text
Turn · advance

“Next” ticks the concept, logs the turn, and may compile notes

advance_lesson_concept ticks the current item, appends a concept event to .tc/session.jsonl, and appends a token-minimal entry to the course memlog. When the final concept is ticked, it automatically calls compile_notes and marks the section review.

tick_concept → append_session_event → compile_notes
Notes · path bug

The human chapter notes are not the file that gets updated

compile_notes finds .tc/course.toml, then sets course_dir = manifest_file.parent. That parent is courses/<slug>/.tc/, so the “flat chapter” is written to .tc/notes/chapter-XX.md. The scaffold at notes/chapter-XX.md stays untouched.

notes_compiler.py → manifest_file.parent / "notes"
Close · no gate

Completion is a state flip, not a conversation

There is no section-close prompt. The learner is not asked to review the compiled notes and approve closure. session.jsonl is not cleared. The next section can be resolved by the normal “first not-started” rule immediately.

no close gate · no unlink/truncate of session.jsonl
Assessment · loose semantics

A practical review can complete the whole course

practical_evaluator.py review --verdict PASS is a caller-supplied verdict. On PASS it sets the course and all chapters and all sections to completed. The lesson-level evaluate-lesson path is a keyword score with a 70-point threshold, not an AI code review.

verdict == PASS → course.status = completed
The teaching invariant is not enforced The proposal correctly says teaching must always require learner verification and sign-off. The current runtime has no such gate. A learner can reach the next section through the ordinary “next” flow; a diagnostic PASS or practical PASS can mark completion without a close conversation.

What course correction should preserve

One front door

A learner should not need to know whether the correct path is the skill, the dispatcher, a gate command, or a teacher command.

Consent where it matters

Source selection, roadmap approval, and section closure are the learner’s decisions. Unattended creation is a convenience, not a license to skip closure.

Notes as the human artifact

The learner should see the compiled chapter notes at the root of the course. Everything else can be machine substrate, provided it is in the right place.

Evidence over labels

A “100% coverage” line is only useful if it is computed from the sources the course actually used. A badge is not evidence.

Memory with granularity

Course-level memory is not enough when the learner asked for the decision history of a specific section or chapter.

A dashboard that is actually alive

It should be generated from the same state the engines write, and it should still work when opened offline.
